按下键盘上的 A，屏幕上出现一个字母，文件里也可以保存这个字母。但存储设备最终记录的是比特：字母怎样与一串 0 和 1 建立联系？

我们需要一套共同的约定，为字符分配编号，再规定怎样表示这些编号。ASCII 就是一套这样的约定。它的范围很小，却把理解文本编码时最重要的几层关系展示得很清楚。

## 比特、字节与解释规则

一个比特（bit）有两种取值，通常写作 0 和 1。本文按照现代计算机中的常见约定，把 8 个比特称为一个字节（byte）。

八个比特共有 256 种组合。作为无符号整数时，一个字节可以表示 0 到 255：

```text
00000000 → 0
00000001 → 1
...
11111111 → 255
```

但 `01000001` 这串比特本身没有写着「我是字母」。把它作为无符号整数解释，数值是 65；按照 ASCII 解释，它对应字符 A。放到其他数据格式中，这个字节还可以参与表示颜色、声音或指令。

因此，读取数据时既要有字节，也要知道<strong>应该采用什么解释规则</strong>。文本编码解决的，就是文字与数值表示之间的约定问题。

## 为什么编码资料喜欢使用十六进制

二进制直接展示每一位，但一长串 0 和 1 不方便阅读。十六进制把每四个比特写成一位数字，使用 0～9 和 A～F 表示 0～15。

例如，把一个字节分为两组：

```text
0100 0001
  4    1
```

因此，下面三种写法表示同一个数值：

| 写法 | 进制 | 数值 |
| --- | --- | ---: |
| `01000001` | 二进制 | 65 |
| `65` | 十进制 | 65 |
| `0x41` | 十六进制 | 65 |

`0x` 是程序中常见的十六进制前缀。有些资料会使用下标或其他记法。进制改变的是数值的书写方式，数值本身没有变化。

以后看到字节序列 `48 65 6C 6C 6F`，首先要确认资料采用了十六进制，而不是把每一项都当成十进制数。

## ASCII 怎样给字符编号

ASCII 的全称是 American Standard Code for Information Interchange，通常译为「美国信息交换标准代码」。它为一组字符与控制功能安排了编号，便于不同设备交换文本。

标准 ASCII 使用 7 位，共有 128 个编码位置，编号为 0～127。存入常见的 8 位字节时，可以把最高位设为 0。比如字符 A 的编号是 65，对应字节 `01000001`。

其中一些常见条目是：

| 字符或功能 | 十进制 | 十六进制 | 放入一个字节后的二进制 |
| --- | ---: | --- | --- |
| 空格 SP | 32 | `20` | `00100000` |
| `0` | 48 | `30` | `00110000` |
| `9` | 57 | `39` | `00111001` |
| `A` | 65 | `41` | `01000001` |
| `Z` | 90 | `5A` | `01011010` |
| `a` | 97 | `61` | `01100001` |
| `z` | 122 | `7A` | `01111010` |

这些编号使得不同系统可以围绕同一张表交换数据。发送方把 A 表示为 65，接收方按照同一规则把它还原为 A。

ASCII 中的英文字母和数字按顺序排列：大写字母在 65～90，小写字母在 97～122，数字字符在 48～57。这解释了很多程序里看起来特殊的数字。

例如，大写 A 与小写 a 的编号相差 32。但这种关系只适用于这些具体的 ASCII 字母，不能直接推广为所有语言的大小写转换规则。

## 数字 5 与字符「5」

整数 5 表示一个数值；字符串 `"5"` 包含一个数字字符。ASCII 为字符 5 分配的编号是 53：

```text
字符 "5" → ASCII 编号 53 → 字节 00110101
```

类似地，文本 `"65"` 包含两个字符，它的 ASCII 字节是：

```text
"6" → 54 → 0x36
"5" → 53 → 0x35

"65" → 36 35
```

而字符 A 只对应一个 ASCII 字节 `41`。虽然 A 的编号是 65，保存 A 和保存文本 `"65"` 仍然是不同的操作。

这也解释了为什么从文本读取数字时需要转换：程序需要把数字字符组成的字符串，解析为能够参与运算的数值。

## 空格和控制字符也是数据

ASCII 不只有能画在屏幕上的字母。编号 0～31 以及 127 对应控制功能；32 是空格；32～126 通常称为可打印字符范围，其中空格占据位置但没有可见笔画。

几个常见条目值得单独认识：

| 名称 | 十进制 | 常见写法 | 作用或含义 |
| --- | ---: | --- | --- |
| NUL | 0 | `\0` | 空字符；某些接口用它表示字符串结束 |
| HT | 9 | `\t` | 水平制表符 |
| LF | 10 | `\n` | 换行，Line Feed |
| CR | 13 | `\r` | 回车，Carriage Return |
| SP | 32 | 空格 | 分隔与排版 |
| DEL | 127 | — | 删除控制字符 |

回车与换行的名称来自设备上的不同动作。文本文件中常见单独的 LF，也能遇到 CR 与 LF 组成的 `\r\n`。一个字符串在显示上换了一行，底层可能包含一个或两个控制字符。

在 Python 这样的语言中，源代码里的 `"\n"` 是使用转义写法构造一个换行字符；`"\\n"` 则包含反斜杠与字母 n。源代码怎样书写字符，与运行时字符串实际包含什么，需要分别观察。

空格也应如此理解。在我们的分词动画里，`␣` 用来让原文中的空格可见。真实空格的 ASCII 编号是 32；可见符号 `␣` 是展示时使用的另一个字符。动画做的是给空格加一个可读的显示标记，原文仍然保留实际空格。

## 用 Python 观察 ASCII

Python 的 `ord()` 返回单个字符的 Unicode 码点，`chr()` 完成相反的转换。Unicode 的前 128 个码点与 ASCII 编号保持一致，因此可以先用它们观察 ASCII 范围：

```python
ord("A")       # 65
chr(65)        # 'A'
ord("5")       # 53
int("5")       # 5
```

要明确观察 ASCII 编码后的字节，可以直接指定编码：

```python
text = "Hello, A!"
raw = text.encode("ascii")

print(raw)                 # b'Hello, A!'
print(list(raw))           # [72, 101, 108, 108, 111, 44, 32, 65, 33]
print(raw.hex(" "))        # 48 65 6c 6c 6f 2c 20 41 21
print(raw.decode("ascii")) # Hello, A!
```

这里的 `b'Hello, A!'` 是 Python 对字节对象的显示形式：可打印 ASCII 字节可以直接显示为对应字符。`list()` 把字节值列成整数，`hex()` 则提供另一种便于检查的写法。

也可以观察不可见字符：

```python
raw = "A B\n".encode("ascii")
print(list(raw))       # [65, 32, 66, 10]
print(raw.hex(" "))    # 41 20 42 0a
```

字符串中有字母、空格和换行，每一项都参与编码。程序如果随意去掉空白，就已经改变了原始文本。

## 128 个位置为什么不够

ASCII 可以表示这里使用的英文字母，却不能独立表示汉字、许多带重音的字母和其他文字：

```python
try:
    "猫".encode("ascii")
except UnicodeEncodeError:
    print("ASCII 中没有这个字符")
```

这不是「猫」无法被计算机保存，而是所选编码没有为它提供表示方式。

一种扩展方向是利用一个字节剩下的取值范围。但额外增加 128 个位置，仍然无法覆盖世界上的文字；不同系统也可能为相同字节安排不同的字符。因此，「扩展 ASCII」这个名称本身不足以确定唯一的编码表。

面向不同地区与文字的编码陆续出现，包括中文环境中的 GB2312、GBK、GB18030，以及处理繁体中文时会遇到的 Big5 等。它们有各自的历史与规则。交换文本时，如果双方使用不同的解释方式，同一批字节就可能产生错误的文字。

继续扩大各自的表，并不能自动解决跨系统交流的问题。我们还需要共同的字符标准，以及能够表示这些字符的编码形式。

## 从 ASCII 走向 Unicode

[Unicode](/blog/unicode/) 为更广泛的文字提供统一的字符与码点体系，同时规定 UTF-8、UTF-16、UTF-32 等编码形式。ASCII 中的字符保留了原来的编号；采用 UTF-8 编码时，这些字符也保留了原来的单字节表示。

因此，一段完全由 ASCII 范围字符组成的文本，在 ASCII 和 UTF-8 下有相同的字节序列。这为旧文本、协议与软件提供了重要的兼容基础。

理解 ASCII 之后，可以继续在 Unicode 篇中追踪「猫」和 Emoji：它们怎样获得码点，又怎样被编码成多个字节。回到 [Tokenization](/blog/cs336-tokenization/) 时，也就能分清字符编号、字节值和词表编号各自在描述哪一层数据。
