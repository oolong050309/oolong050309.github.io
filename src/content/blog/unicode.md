[ASCII](/blog/ascii/) 为英文字母、数字和控制字符安排了统一编号。但一段日常文本可能同时包含英文、汉字、数学符号和 Emoji。我们需要能够跨文字系统交换文本的共同约定。

Unicode 为字符定义码点、名称、属性和相关处理规则，也规定 UTF-8、UTF-16、UTF-32 等编码形式。理解它时，可以沿着一条具体的路径观察：<strong>字符怎样对应码点，码点怎样变成字节，字节又怎样还原成文本。</strong>

## 字符、码点、码元与字形

先把几个经常一起出现的词放到各自的位置上：

| 概念 | 描述什么 | 例子 |
| --- | --- | --- |
| 字符 | 文本中具有身份的抽象元素 | 拉丁字母 A、汉字「猫」 |
| 码点（code point） | Unicode 编码空间中的数值位置 | `U+0041`、`U+732B` |
| 码元（code unit） | 某种编码形式的基本单位 | UTF-8 的 8 位码元、UTF-16 的 16 位码元 |
| 字节（byte） | 本文采用的 8 位数据单位 | 十六进制字节 `E7` |
| 字形（glyph） | 字体与排版系统绘制出的形状 | 不同字体中的 A |
| 字素簇（grapheme cluster） | 按分段规则组合起来的文本单位 | 字母与组合重音、部分 Emoji 序列 |

例如，「猫」的码点是 `U+732B`。选择 UTF-8 后，它会被表示为三个字节 `E7 8C AB`。屏幕上具体画出什么样的「猫」，还需要字体和排版系统参与。

这些概念在简单英文里经常刚好对应同一个数量，因此容易被混用。遇到组合字符和 Emoji 时，它们的差别就会显现出来。

## 码点怎样书写

Unicode 用 `U+` 后接 4～6 位十六进制数来书写码点。不足四位时在左边补零，如 `U+0041`。超过四位就按实际位数写，如 `U+1F600`。补零只是码点的书写约定，`A` 的 UTF-8 编码仍然只有一个字节。

| 文本 | 码点 | 十进制数值 |
| --- | --- | ---: |
| `A` | `U+0041` | 65 |
| `猫` | `U+732B` | 29483 |
| `😀` | `U+1F600` | 128512 |

`U+732B` 表示数值为十六进制 732B 的码点。它的书写长度不能直接用来判断存储这个字符需要几个字节。

可以用 Python 查看：

```python
import unicodedata

for ch in ["A", "猫", "😀"]:
    print(ch, f"U+{ord(ch):04X}", unicodedata.name(ch))
```

ASCII 的前 128 个编号也保留在 Unicode 中。因此，`ord("A")` 返回的 65 既与 ASCII 编号一致，也对应 Unicode 码点 `U+0041`；`ord("猫")` 则已经超出 ASCII 的表示范围。

### 有多少个码点，收录了多少个字符？

从 `U+0000` 到 `U+10FFFF`，每个整数都是一个码点，也就是编码空间里的一个位置。这个空间分为 17 个平面，每个平面有 65,536（2¹⁶）个位置。第 0 平面叫基本多文种平面（BMP），从 `U+0000` 到 `U+FFFF`。其余 16 个平面称为补充平面。

以 Unicode 17.0 为例，全部 **1,114,112 个位置**按用途可分为下表六类。每个位置只算一次。表中范围均包含两端。

| 用途 | 位置数 | 在编码空间的什么位置 |
| --- | ---: | --- |
| 图形字符和格式字符（已收录字符数） | 159,801 | 分散在多个区段。例如，大写英文字母占 `U+0041`–`U+005A`，「猫」在 `U+732B`，零宽连接符在 `U+200D`。 |
| 控制码 | 65 | `U+0000`–`U+001F` 和 `U+007F`–`U+009F`，其中 `U+000A` 表示换行。 |
| 私用码点 | 137,468 | `U+E000`–`U+F8FF`、`U+F0000`–`U+FFFFD`、`U+100000`–`U+10FFFD`。使用者自行约定每个位置代表什么。 |
| 代理码点 | 2,048 | `U+D800`–`U+DBFF` 用于 UTF-16 代理对的第一项，`U+DC00`–`U+DFFF` 用于第二项。 |
| 非字符码点 | 66 | `U+FDD0`–`U+FDEF` 共 32 个，加上 17 个平面各自最后两个位置（如 `U+FFFE`、`U+FFFF`），共 32 + 17 × 2 个。这些位置永久留作内部用途。 |
| 尚未分配的位置 | 814,664 | 散布在前五类之外的区段。例如，`U+0378`–`U+0379` 在 17.0 版仍然空着，可留给未来的字符。 |

读统计表时，可以逐层相加：

- **已分配字符**包括前三行。已收录的图形和格式字符，加上控制码和私用码点，共 159,801 + 65 + 137,468 = **297,334**。
- **已分配位置（已指定用途的码点）**包括前五行。已分配字符，加上代理码点和非字符码点，共 297,334 + 2,048 + 66 = **299,448**。例如，`U+FFFF` 虽然没有对应字符，却已经被指定为非字符，今后也不会分给新字符。
- **位置总数**包括全部六行，即 299,448 个已指定用途的位置，加上 814,664 个尚未分配的位置，共 **1,114,112**。

为什么要留出代理码点？比如 `😀` 的码点是 `U+1F600`，超出了单个 16 位码元能存下的最大值 `FFFF`。UTF-16 用两个码元 `D83D DE00` 合起来表示它。解码器读到前一个值，就知道要和后一个值配对，才能还原出这个笑脸。这两个值各自都不代表独立字符。整个编码空间去掉代理码点，余下的两段（`U+0000`–`U+D7FF` 和 `U+E000`–`U+10FFFF`）构成 **Unicode 标量值**的范围。

### 一个码点属于哪个平面、哪个区块？

把码点写成十六进制，从右边数出四位，就能看出它属于哪个**平面**。「猫」的 `U+732B` 只有四位，在第 0 平面。`😀` 的 `U+1F600` 可以拆成 `1 | F600`，在第 1 平面。按本文采用的 Unicode 17.0，各平面的用途如下。

| 平面 | 码点范围（含两端） | 主要用途 |
| --- | --- | --- |
| 0（BMP） | `U+0000`～`U+FFFF` | 基本多文种平面，包括拉丁字母、常用汉字、标点等。 |
| 1（SMP） | `U+10000`～`U+1FFFF` | 补充多文种平面，包括历史文字、乐谱符号和许多 Emoji。 |
| 2（SIP） | `U+20000`～`U+2FFFF` | 补充表意文字平面，收录中日韩统一表意文字的多个扩展区。 |
| 3（TIP） | `U+30000`～`U+3FFFF` | 第三表意文字平面，继续容纳汉字扩展区。 |
| 4～13 | `U+40000`～`U+DFFFF` | 17.0 版尚未在这些平面收录字符。 |
| 14（SSP） | `U+E0000`～`U+EFFFF` | 补充专用平面，包括标签字符和补充变体选择符。变体选择符可以跟在字符后面指定字形变体。 |
| 15、16 | `U+F0000`～`U+FFFFF`、`U+100000`～`U+10FFFF` | 两个补充私用平面，分别称为 SPUA-A、SPUA-B。每个平面最后两个位置仍是非字符。 |

**区块（block）**是平面内有名称的一段连续码点，用于把相关字符编排在一起。区块大小不一，内部也可能留有空位。例如，「猫」属于第 0 平面的「中日韩统一表意文字」区块（`U+4E00`～`U+9FFF`）。`A` 也在第 0 平面，却属于「基本拉丁文」区块（`U+0000`～`U+007F`）。

## Unicode 与 UTF 的关系

有了码点，还需要规定怎样在文件或网络中表示它。Unicode 定义了三种常见编码形式：

- <strong>UTF-8：</strong>使用 8 位码元，一个标量值对应 1～4 个码元。
- <strong>UTF-16：</strong>使用 16 位码元，一个标量值对应 1 个或 2 个码元。
- <strong>UTF-32：</strong>使用 32 位码元，一个标量值对应 1 个码元。

其中 8、16、32 指的是码元的位数。把这些码元序列保存为字节时，还可能需要考虑多字节码元的字节序。

因此，同一个「猫」可以有不同的字节表示：

| 编码方式 | 字节序列，不含 BOM |
| --- | --- |
| UTF-8 | `E7 8C AB` |
| UTF-16BE（大端） | `73 2B` |
| UTF-16LE（小端） | `2B 73` |
| UTF-32BE（大端） | `00 00 73 2B` |

正确使用相应规则进行解码，都可以得到同一个码点。后文的[「字节序与 BOM」](#字节序与-bom)会介绍大端和小端怎样排列字节。

## UTF-8

UTF-8 用不同长度的字节序列表示不同范围的标量值。首字节包含长度相关的结构信息，后续字节以二进制 `10` 开头：

| 码点范围 | 字节数 | 二进制结构 |
| --- | ---: | --- |
| `U+0000`～`U+007F` | 1 | `0xxxxxxx` |
| `U+0080`～`U+07FF` | 2 | `110xxxxx 10xxxxxx` |
| `U+0800`～`U+FFFF`，排除代理范围 | 3 | `1110xxxx 10xxxxxx 10xxxxxx` |
| `U+10000`～`U+10FFFF` | 4 | `11110xxx 10xxxxxx 10xxxxxx 10xxxxxx` |

表中的 x 用来存放码点的信息位，固定的前缀用于识别字节结构。编码还必须满足范围与最短表示等要求，不能只检查前缀形状。

**范围**决定哪些值可以编码。UTF-8 只能表示 Unicode 标量值。例如，`U+D800` 属于代理码点，`0x110000` 超过了最大码点 `U+10FFFF`，两者都没有合法的 UTF-8 编码。

**最短表示**决定一个值该用几个字节。字母 `A` 的码点是 65，二进制是 `1000001`，正好能填进单字节模板 `0xxxxxxx`，得到 `01000001`（十六进制 `41`）。如果硬把它填进两字节模板 `110xxxxx 10xxxxxx`，右边的 6 个空位填 `000001`，左边剩下的 `1` 补成 5 位 `00001`，拼出来就是 `11000001 10000001`（`C1 81`）。这串字节的前缀看起来符合模板，但 65 只需一个字节，`C1 81` 属于**过长编码**，UTF-8 解码器应当把它判为无效。

### 先看 ASCII 范围

`A` 的码点是 `U+0041`，位于单字节范围。先把码点写成二进制：

```text
0x41 → 1000001
```

单字节模板 `0xxxxxxx` 有 7 个信息位。把这 7 位填在固定前缀 `0` 后面：

```text
0 + 1000001 → 01000001
```

于是得到：

```text
二进制：01000001
十六进制：41
十进制字节值：[65]
```

这与 `A` 的 ASCII 编码相同。整个 ASCII 范围的字符都可以按 UTF-8 原样读取。

### 手算一个「猫」字

「猫」的码点是 `U+732B`，位于三字节范围。先把码点写成二进制：

```text
0x732B → 0111 0011 0010 1011
```

三字节模板有 4＋6＋6 个信息位。从右向左分组：

```text
0111 | 001100 | 101011
```

再把三组信息填入固定前缀：

```text
1110 + 0111   → 11100111
10   + 001100 → 10001100
10   + 101011 → 10101011
```

于是得到：

```text
二进制：11100111 10001100 10101011
十六进制：E7 8C AB
十进制字节值：[231, 140, 171]
```

用标准库验证：

```python
text = "猫"
raw = text.encode("utf-8")

print(ord(text))           # 29483
print(raw.hex(" "))        # e7 8c ab
print(list(raw))           # [231, 140, 171]
print(raw.decode("utf-8")) # 猫
```

29483 是码点的十进制数值；231、140、171 是编码后三个字节各自的数值。它们在描述不同层次。

### 四个字节与反向解码

`😀` 的码点是 `U+1F600`，位于四字节范围。先把码点写成二进制：

```text
0x1F600 → 1 1111 0110 0000 0000
```

四字节模板 `11110xxx 10xxxxxx 10xxxxxx 10xxxxxx` 有 3＋6＋6＋6 个信息位。码点的二进制有 17 位，在左边补 4 个零，正好填满 21 位。从右向左每 6 位分一组，分出三组后，最左边留下 3 位：

```text
000 | 011111 | 011000 | 000000
```

按从左到右的顺序填入模板。第一组前面加 `11110`，后面三组各加 `10`：

```text
11110 + 000    → 11110000
10    + 011111 → 10011111
10    + 011000 → 10011000
10    + 000000 → 10000000
```

于是得到：

```text
二进制：11110000 10011111 10011000 10000000
十六进制：F0 9F 98 80
十进制字节值：[240, 159, 152, 128]
```

反过来解码时，首字节的 `11110` 表明这组共有四个字节。确认序列合法后，去掉首字节的 `11110` 和三个后续字节各自的 `10`。把剩下的四组信息位按原顺序拼起来，就还原出码点 `U+1F600`，也就是 `😀`。

因此，「一个汉字占几个字节」需要带上编码和具体字符：在 UTF-8 中，许多常用汉字占三个字节，补充平面的汉字占四个字节。

### 任意一段字节都能解码吗

`10xxxxxx` 形式的后续字节不能单独作为字符起点；需要三个字节的序列也可能只收到两个。除此之外，过长编码、代理码点对应的编码和超出 `U+10FFFF` 的表示都不属于合法 UTF-8。

文件或网络的分块边界也可能切在一个字符中间。增量解码器需要保留尚未完整的序列，等后续字节到达后再继续。处理过程中采用什么单位切片，会影响得到的片段能否独立解码。

## UTF-16 与代理对

UTF-16 使用 16 位码元。BMP 中的标量值使用一个码元；补充平面的标量值则使用一对码元，称为<strong>代理对（surrogate pair）</strong>。

以 `😀` 为例：

```text
U+1F600 → D83D DE00
```

计算时，先从码点减去 `0x10000`：

```text
0x1F600 - 0x10000 = 0xF600
```

再把结果拆为高、低各 10 位：高 10 位加到 `0xD800` 上，低 10 位加到 `0xDC00` 上，得到 `D83D` 与 `DE00`。两个码元共同表示原来的一个标量值。

这使得 UTF-16 中，一个码点可以占两个或四个字节。只截取代理对的一半，会得到不完整的表示。

### 字节序与 BOM

一个 16 位码元由两个字节组成。高位字节在前，叫大端（BE）；低位字节在前，叫小端（LE）。例如 `0x732B`：

```text
UTF-16BE：73 2B
UTF-16LE：2B 73
```

代理对也按码元顺序保存，字节序决定的是每个码元内部字节的排列。例如 `D83D DE00` 的 UTF-16LE 字节为 `3D D8 00 DE`。

BOM（Byte Order Mark）是在文本流开头用作标记的 `U+FEFF`。如果文件用 BOM 指明字节序，同一个码点在开头会写成下面几种字节序列。

| 编码 | 大端 BOM（十六进制） | 小端 BOM（十六进制） |
| --- | --- | --- |
| UTF-16 | `FE FF` | `FF FE` |
| UTF-32 | `00 00 FE FF` | `FF FE 00 00` |

UTF-32 用四个字节保存数值 `0x0000FEFF`。大端从最高位字节 `00` 开始写，小端从最低位字节 `FF` 开始写，所以表里的两种标记恰好按相反顺序排列。

UTF-8 也可能带有 `EF BB BF` 形式的 BOM。UTF-8 的码元本身只有一个字节，这个标记用于识别编码，不能据此再区分大小端。具体格式如何处理 BOM，需要遵循该格式和解析器的约定。

## UTF-32 与表示长度的取舍

UTF-32 为每个 Unicode 标量值使用一个 32 位码元，也就是四个字节。它使码点与码元数量保持一致，但一段由多个码点组成的可见文本单位，仍然需要多个码元。

比较几种编码的字节长度，可以看到不同取舍：

| 文本 | UTF-8 | UTF-16 | UTF-32 |
| --- | ---: | ---: | ---: |
| `A` | 1 | 2 | 4 |
| `猫` | 3 | 2 | 4 |
| `😀` | 4 | 4 | 4 |
| `ABC猫` | 6 | 8 | 16 |

这里比较的是编码后的数据，不含 BOM，也不包含程序对象、文件格式或网络协议的额外开销。

这些编码形式都能够表示相同的 Unicode 标量值序列。体积差别取决于具体文本，编解码和处理成本也需要结合应用场景讨论。

## 一个看起来完整的字符，可能包含多个码点

`é` 可以由单个码点 `U+00E9` 表示，也可以由字母 e 与组合重音组成：

```text
U+0065 + U+0301
```

这两个序列可以有相同的显示效果，码点数量和字节序列却不同。

`👩‍💻` 由三个码点组成。中间的 `U+200D` 是零宽连接符（ZWJ），把人物 `👩` 和电脑 `💻` 连起来。要加上中等肤色，就把修饰符 `🏽`（`U+1F3FD`）放在人物和连接符之间。

```text
👩‍💻  → U+1F469 + U+200D + U+1F4BB
👩🏽‍💻  → U+1F469 + U+1F3FD + U+200D + U+1F4BB
```

加上肤色后，码点从 3 个变成 4 个。两种写法各自仍是一个字素簇，在支持这些序列的环境中都显示为一个表情。

Unicode 的<strong>扩展字素簇</strong>分段规则，为光标移动、文本截断等操作提供了接近用户感知的边界。它是文本处理规则，不等于字体最终画出的字形数，也不等于屏幕宽度。

表中的「默认扩展字素簇数」是按 Unicode 的默认规则把文本分组后得到的组数。`A👩🏽‍💻` 有 5 个码点，依次是字母 `A`、人物 `👩`、肤色修饰符 `🏽`、零宽连接符和电脑 `💻`。按这套规则，`A` 单独成一组，后四个码点合成一组 `👩🏽‍💻`，所以一共是 2 个字素簇。

| 文本 | UTF-8 字节数 | 码点数 | UTF-16 码元数 | 默认扩展字素簇数 |
| --- | ---: | ---: | ---: | ---: |
| `A` | 1 | 1 | 1 | 1 |
| `猫` | 3 | 1 | 1 | 1 |
| `😀` | 4 | 1 | 2 | 1 |
| `é`，使用 `U+00E9` | 2 | 1 | 1 | 1 |
| `e`＋`U+0301` | 3 | 2 | 2 | 1 |
| `👩‍💻` | 11 | 3 | 5 | 1 |
| `👩🏽‍💻` | 15 | 4 | 7 | 1 |

因此，设计「最多输入 20 个字符」时，需要先决定限制的是字节、码点还是字素簇。按字节截断可能切断 UTF-8 序列；按码点截断也可能拆开组合字符或 Emoji。

### 全角、半角与显示宽度

在按列对齐的终端里，同样是一个字素簇，字母 `A` 通常占一列，全角字母 `Ａ` 通常占两列。换一组片假名来比较，还能看到显示宽度和存储长度的区别。

| 文本 | 码点 | 东亚宽度属性 | 终端常见列数 | UTF-8 字节数 |
| --- | --- | --- | ---: | ---: |
| `A` | `U+0041` | Na（窄） | 1 | 1 |
| `Ａ` | `U+FF21` | F（全角） | 2 | 3 |
| `ｶ` | `U+FF76` | H（半角） | 1 | 3 |
| `カ` | `U+30AB` | W（宽） | 2 | 3 |

后两行都是片假名「カ」的写法，UTF-8 都占三个字节，显示时却可以相差一列。Unicode 的东亚宽度属性（`East_Asian_Width`）记录这些排版差异。除表中四类外，还有 A（宽度有歧义，如 `·`）和 N（中性）。终端会结合自身规则决定列宽。在按比例排版的网页里，实际像素宽度还取决于字体和字号。

## Python 与 JavaScript 为什么会给出不同长度

Python 的 `str` 按 Unicode 码点提供常见的长度与索引操作；JavaScript 字符串的长度与索引则以 UTF-16 码元为单位。

Python 中：

```python
for text in ("👩‍💻", "👩🏽‍💻"):
    print(len(text))                  # 码点数：依次为 3、4
    print(len(text.encode("utf-8")))  # UTF-8 字节数：依次为 11、15
```

JavaScript 中：

```javascript
const segmenter = new Intl.Segmenter("zh", { granularity: "grapheme" });
for (const text of ["👩‍💻", "👩🏽‍💻"]) {
  console.log(text.length);                           // UTF-16 码元数：5、7
  console.log([...text].length);                      // 码点数：3、4
  console.log(new TextEncoder().encode(text).length); // UTF-8 字节数：11、15
  console.log([...segmenter.segment(text)].length);   // 字素簇数：1、1
}
```

这些结果采用了不同的计量单位。对于合法 Unicode 文本，JavaScript 的字符串迭代可以按码点访问，而普通索引仍然按码元访问。语言定义的操作语义，也不能直接当作引擎内部内存布局的说明。

字体则负责另一层工作：同一个码点可以在不同字体中显示为不同形状；多个码点也可能参与一个字形。遇到缺字方框时，需要检查字体支持，不能仅凭显示异常就认定原始字节的编码错了。

## 看起来一样的文字，怎样比较

两种 `é` 可以显示相同，直接进行字符串比较却得到不同结果：

```python
import unicodedata

a = "\u00e9"
b = "e\u0301"

print(a == b)  # False
print(unicodedata.normalize("NFC", a) ==
      unicodedata.normalize("NFC", b))  # True
```

Unicode 规范化为特定等价关系提供一致表示：

| 形式 | 主要过程 |
| --- | --- |
| NFD | 规范分解与重排 |
| NFC | 规范分解、重排，再按规则组合 |
| NFKD | 兼容分解与重排 |
| NFKC | 兼容分解、重排，再按规则组合 |

规范等价用于处理这类组合与分解表示；兼容等价还会合并某些排版或形式区别。例如，NFKC 可以把全角字母 `Ａ` 和带圈数字 `①` 转为 `A` 与 `1`。

选择规范化形式，要看任务希望保留哪些区别。搜索、去重与原始文本存档可能有不同要求。规范化、大小写折叠和排序规则也各自解决不同问题。

规范化还可能改变码点序列和编码后的字节。因此，讨论文本能否原样还原时，需要说明是否做过规范化等预处理。

## 乱码发生在哪一步

处理文件与网络数据时，程序需要在文本和字节之间转换：

```text
文本 → encode → 字节 → 保存或传输 → 字节 → decode → 文本
```

如果编码与解码采用不同规则，就可能产生错误文本：

```python
original = "café"
raw = original.encode("utf-8")
wrong = raw.decode("latin-1")

print(raw.hex(" ")) # 63 61 66 c3 a9
print(wrong)        # cafÃ©
```

最后两个 UTF-8 字节本来共同表示 é，却被另一种规则分别解释成字符。若中间没有发生替换或信息丢失，这个特定过程可以反向恢复：

```python
wrong = "cafÃ©"
restored = wrong.encode("latin-1").decode("utf-8")
print(restored)  # café
```

但已经丢弃的字节或替换掉的字符，通常不能只靠错误显示后的文本完整恢复。因此，排查时应尽量查看原始字节与实际使用的编解码规则。

### 两个替换字符怎样变成「锟斤拷」

假设文件里有两个字节 `FF FF`。单个 `FF` 无法按 UTF-8 解码。用替换策略读取这两个字节，每次出错都会写入一个替换字符 `�`（`U+FFFD`），于是得到 `��`。再把这段文本保存成 UTF-8，每个 `�` 都写成三个字节 `EF BF BD`。

如果下一个程序按 [GBK](/reference/legacy-encodings/#gbk-与其他地区编码) 打开这份文件，同样的六个字节就有了另一种分组。竖线标出字符之间的边界。

```text
UTF-8   EF BF BD│EF BF BD   → � �
GBK     EF BF│BD EF│BF BD   → 锟 斤 拷
```

按 GBK 查表，`EF BF` 对应「锟」，`BD EF` 对应「斤」，`BF BD` 对应「拷」。中间的「斤」恰好跨过了原来的字符边界。它的 `BD` 取自第一个 `�` 的末尾，`EF` 取自第二个 `�` 的开头。把「锟斤拷」按 GBK 编回字节，再按 UTF-8 读取，可以找回 `��`。至于最初出错的是哪些字节，第一次替换时就已经丢失了这条信息。

### 为什么调试输出里会出现「烫烫烫」

在 Visual C++ 的某些调试配置下，编译器会用 `0xCC` 填充一段栈内存，方便检查程序对局部变量的使用。假设程序在栈上的字符缓冲区里写了一小段文字，输出时却用了整个缓冲区的容量，正文后面残留的 `CC` 就可能被一起送到终端。

如果终端按 GBK 解码，`CC CC` 恰好对应汉字「烫」。连续六个这样的字节就会显示成三个「烫」。

```text
CC CC │ CC CC │ CC CC
  烫      烫      烫
```

这条路径用不到替换字符 `�`。调试填充解释了字节为什么重复，GBK 的映射解释了为什么重复出现的恰好是「烫」。

### 遇到非法字节时

以缺少最后一个字节的「猫」为例：

```python
raw = b"\xe7\x8c"

try:
    raw.decode("utf-8", errors="strict")
except UnicodeDecodeError:
    print("UTF-8 序列不完整")

print(raw.decode("utf-8", errors="replace")) # �
print(repr(raw.decode("utf-8", errors="ignore"))) # ''
```

`strict` 报告错误，`replace` 产生替换字符，`ignore` 丢弃无法解码的部分。它们对应不同的数据处理结果。

### 文件、编码声明与转义

读写文本文件时，可以显式指定编码：

```python
from pathlib import Path

path = Path("unicode-example.txt")
path.write_text("猫😀", encoding="utf-8")

print(path.read_bytes().hex(" ")) # e7 8c ab f0 9f 98 80
print(path.read_text(encoding="utf-8")) # 猫😀
```

HTML 中的 `<meta charset="UTF-8">` 和 HTTP 中与编码相关的声明，帮助接收方选择解释规则；修改声明本身，并不会自动把原有文件转成另一种编码。

HTML 和 XML 还允许在文本里写**字符引用**。例如，要在页面上显示「猫 & 狗」，可以把段落写成 `<p>&#x732B; &amp; 狗</p>`。浏览器先按文件编码读出源码，再在解析标记时把 `&#x732B;` 还原成「猫」、把 `&amp;` 还原成 `&`。

数字引用使用 Unicode 码点。`&#29483;` 和 `&#x732B;` 分别用十进制和十六进制写出了同一个「猫」字。另一种写法是用名称，例如 `&lt;` 表示小于号。XML 预定义了 `&amp;`、`&lt;`、`&gt;`、`&quot;` 和 `&apos;` 五个实体。HTML 内置的名称更多，例如 `&nbsp;` 表示不换行空格。在没有额外实体声明的 XML 中，可以用数字引用 `&#xA0;` 写出同一个空格。

源代码里的转义则属于书写规则：

```python
text = "\u732b"
literal = r"\u732b"

print(text, len(text))       # 猫 1
print(literal, len(literal)) # \u732b 6
```

第一个字符串包含「猫」，第二个包含反斜杠、u 和四个十六进制数字字符。看到 `\uXXXX` 时，需要结合所在语言或数据格式，判断它是转义语法还是普通文本。
