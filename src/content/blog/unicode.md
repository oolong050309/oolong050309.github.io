[ASCII](/blog/ascii/) 为英文字母、数字和控制字符安排了统一编号。但一段日常文本可能同时包含英文、汉字、数学符号和 Emoji。我们需要能够跨文字系统交换文本的共同约定。

Unicode 为字符定义码点、名称、属性和相关处理规则，也规定 UTF-8、UTF-16、UTF-32 等编码形式。理解它时，可以沿着一条具体的路径观察：<strong>字符怎样对应码点，码点怎样变成字节，字节又怎样还原成文本。</strong>

## 字符、码点、码元与字形

先把几个经常一起出现的词放到各自的位置上：

| 概念 | 描述什么 | 例子 |
| --- | --- | --- |
| 字符 | 文本中具有身份的抽象元素 | 拉丁字母 A、汉字「猫」 |
| 码点（code point） | Unicode 编码空间中的数值位置 | `U+0041`、`U+732B` |
| 码元（code unit） | 某种编码形式的基本单位 | UTF-8 的 8 位码元、UTF-16 的 16 位码元 |
| 字节（byte） | 本文采用的 8 位数据单位 | 十六进制字节 `E7` |
| 字形（glyph） | 字体与排版系统绘制出的形状 | 不同字体中的 A |
| 字素簇（grapheme cluster） | 按分段规则组合起来的文本单位 | 字母与组合重音、部分 Emoji 序列 |

例如，「猫」的码点是 `U+732B`。选择 UTF-8 后，它会被表示为三个字节 `E7 8C AB`。屏幕上具体画出什么样的「猫」，还需要字体和排版系统参与。

这些概念在简单英文里经常刚好对应同一个数量，因此容易被混用。遇到组合字符和 Emoji 时，它们的差别就会显现出来。

## 码点怎样书写

Unicode 常用 `U+` 后接十六进制数来表示码点：

| 文本 | 码点 | 十进制数值 |
| --- | --- | ---: |
| `A` | `U+0041` | 65 |
| `猫` | `U+732B` | 29483 |
| `😀` | `U+1F600` | 128512 |

`U+732B` 表示数值为十六进制 732B 的码点。它的书写长度不能直接用来判断存储这个字符需要几个字节。

可以用 Python 查看：

```python
import unicodedata

for ch in ["A", "猫", "😀"]:
    print(ch, f"U+{ord(ch):04X}", unicodedata.name(ch))
```

Unicode 的编码空间从 `U+0000` 到 `U+10FFFF`，划分为 17 个平面，每个平面有 65,536 个位置。第 0 平面叫基本多文种平面（BMP），其余是补充平面。

这个空间包含已分配位置、尚未分配的位置和具有特殊用途的位置。位置总数与已收录字符数需要分别理解。`U+D800`～`U+DFFF` 是代理码点范围；排除这个范围之后的码点值，称为 <strong>Unicode 标量值</strong>。后文讲合法 UTF 编码时，讨论的是这些标量值。

ASCII 的前 128 个编号也保留在 Unicode 中。因此，`ord("A")` 返回的 65 既与 ASCII 编号一致，也对应 Unicode 码点 `U+0041`；`ord("猫")` 则已经超出 ASCII 的表示范围。

## Unicode 与 UTF 的关系

有了码点，还需要规定怎样在文件或网络中表示它。Unicode 定义了三种常见编码形式：

- <strong>UTF-8：</strong>使用 8 位码元，一个标量值对应 1～4 个码元。
- <strong>UTF-16：</strong>使用 16 位码元，一个标量值对应 1 个或 2 个码元。
- <strong>UTF-32：</strong>使用 32 位码元，一个标量值对应 1 个码元。

其中 8、16、32 指的是码元的位数。把这些码元序列保存为字节时，还可能需要考虑多字节码元的字节序。

因此，同一个「猫」可以有不同的字节表示：

| 编码方式 | 字节序列，不含 BOM |
| --- | --- |
| UTF-8 | `E7 8C AB` |
| UTF-16BE | `73 2B` |
| UTF-16LE | `2B 73` |
| UTF-32BE | `00 00 73 2B` |

正确使用相应规则进行解码，都可以得到同一个码点。

## UTF-8

UTF-8 用不同长度的字节序列表示不同范围的标量值。首字节包含长度相关的结构信息，后续字节以二进制 `10` 开头：

| 码点范围 | 字节数 | 二进制结构 |
| --- | ---: | --- |
| `U+0000`～`U+007F` | 1 | `0xxxxxxx` |
| `U+0080`～`U+07FF` | 2 | `110xxxxx 10xxxxxx` |
| `U+0800`～`U+FFFF`，排除代理范围 | 3 | `1110xxxx 10xxxxxx 10xxxxxx` |
| `U+10000`～`U+10FFFF` | 4 | `11110xxx 10xxxxxx 10xxxxxx 10xxxxxx` |

表中的 x 用来存放码点的信息位，固定的前缀用于识别字节结构。编码还必须满足范围与最短表示等要求，不能只检查前缀形状。

### 先看 ASCII 范围

A 的码点是 `U+0041`，使用一个字节：

```text
U+0041 → 01000001 → 41
```

这与 ASCII 的字节完全一致。所有 ASCII 范围字符都有这个性质：一段有效 ASCII 字节序列，也可以直接作为相同文本的 UTF-8 字节序列。

### 手算一个「猫」字

「猫」的码点是 `U+732B`，位于三字节范围。先把码点写成二进制：

```text
0x732B → 0111 0011 0010 1011
```

三字节模板有 4＋6＋6 个信息位。从右向左分组：

```text
0111 | 001100 | 101011
```

再把三组信息填入固定前缀：

```text
1110 + 0111   → 11100111
10   + 001100 → 10001100
10   + 101011 → 10101011
```

于是得到：

```text
二进制：11100111 10001100 10101011
十六进制：E7 8C AB
十进制字节值：[231, 140, 171]
```

用标准库验证：

```python
text = "猫"
raw = text.encode("utf-8")

print(ord(text))           # 29483
print(raw.hex(" "))        # e7 8c ab
print(list(raw))           # [231, 140, 171]
print(raw.decode("utf-8")) # 猫
```

29483 是码点的十进制数值；231、140、171 是编码后三个字节各自的数值。它们在描述不同层次。

### 四个字节与反向解码

`😀` 的码点是 `U+1F600`，需要四个 UTF-8 字节：

```text
U+1F600
→ 11110000 10011111 10011000 10000000
→ F0 9F 98 80
```

解码时，可以识别首字节，读取相应的后续字节，检查合法性，再提取并拼接信息位，恢复码点。

因此，「一个汉字占几个字节」需要带上编码和具体字符：在 UTF-8 中，许多常用汉字占三个字节，补充平面的汉字占四个字节。

### 任意一段字节都能解码吗

`10xxxxxx` 形式的后续字节不能单独作为字符起点；需要三个字节的序列也可能只收到两个。除此之外，过长编码、代理码点对应的编码和超出 `U+10FFFF` 的表示都不属于合法 UTF-8。

文件或网络的分块边界也可能切在一个字符中间。增量解码器需要保留尚未完整的序列，等后续字节到达后再继续。处理过程中采用什么单位切片，会影响得到的片段能否独立解码。

## UTF-16 与代理对

UTF-16 使用 16 位码元。BMP 中的标量值使用一个码元；补充平面的标量值则使用一对码元，称为<strong>代理对（surrogate pair）</strong>。

以 `😀` 为例：

```text
U+1F600 → D83D DE00
```

计算时，先从码点减去 `0x10000`：

```text
0x1F600 - 0x10000 = 0xF600
```

再把结果拆为高、低各 10 位：高 10 位加到 `0xD800` 上，低 10 位加到 `0xDC00` 上，得到 `D83D` 与 `DE00`。两个码元共同表示原来的一个标量值。

这使得 UTF-16 中，一个码点可以占两个或四个字节。只截取代理对的一半，会得到不完整的表示。

### 字节序与 BOM

一个 16 位码元由两个字节组成。高位字节在前，叫大端（BE）；低位字节在前，叫小端（LE）。例如 `0x732B`：

```text
UTF-16BE：73 2B
UTF-16LE：2B 73
```

代理对也按码元顺序保存，字节序决定的是每个码元内部字节的排列。例如 `D83D DE00` 的 UTF-16LE 字节为 `3D D8 00 DE`。

BOM（Byte Order Mark）使用 `U+FEFF` 在字节流开头形成标记。UTF-16BE 中的字节为 `FE FF`，UTF-16LE 中为 `FF FE`，可以帮助识别字节序。

UTF-8 也可能带有 `EF BB BF` 形式的 BOM。UTF-8 的码元本身只有一个字节，这个标记用于识别编码，不能据此再区分大小端。具体格式如何处理 BOM，需要遵循该格式和解析器的约定。

## UTF-32 与表示长度的取舍

UTF-32 为每个 Unicode 标量值使用一个 32 位码元，也就是四个字节。它使码点与码元数量保持一致，但一段由多个码点组成的可见文本单位，仍然需要多个码元。

比较几种编码的字节长度，可以看到不同取舍：

| 文本 | UTF-8 | UTF-16 | UTF-32 |
| --- | ---: | ---: | ---: |
| `A` | 1 | 2 | 4 |
| `猫` | 3 | 2 | 4 |
| `😀` | 4 | 4 | 4 |
| `ABC猫` | 6 | 8 | 16 |

这里比较的是编码后的数据，不含 BOM，也不包含程序对象、文件格式或网络协议的额外开销。

这些编码形式都能够表示相同的 Unicode 标量值序列。体积差别取决于具体文本，编解码和处理成本也需要结合应用场景讨论。

## 一个看起来完整的字符，可能包含多个码点

`é` 可以由单个码点 `U+00E9` 表示，也可以由字母 e 与组合重音组成：

```text
U+0065 + U+0301
```

这两个序列可以有相同的显示效果，码点数量和字节序列却不同。

Emoji 也会出现类似情况。`👩‍💻` 由三个码点构成：

```text
U+1F469  女性人物
U+200D   零宽连接符 ZWJ
U+1F4BB  电脑
```

支持该序列的字体和排版环境可以把它显示为一个组合 Emoji。肤色修饰符、变体选择符和旗帜序列，也会让视觉效果与码点数量之间的关系更加丰富。

Unicode 的<strong>扩展字素簇</strong>分段规则，为光标移动、文本截断等操作提供了接近用户感知的边界。它是文本处理规则，不等于字体最终画出的字形数，也不等于屏幕宽度。

下面这些数量可以同时成立：

| 文本 | UTF-8 字节数 | 码点数 | UTF-16 码元数 | 默认扩展字素簇数 |
| --- | ---: | ---: | ---: | ---: |
| `A` | 1 | 1 | 1 | 1 |
| `猫` | 3 | 1 | 1 | 1 |
| `😀` | 4 | 1 | 2 | 1 |
| `é`，使用 `U+00E9` | 2 | 1 | 1 | 1 |
| `e`＋`U+0301` | 3 | 2 | 2 | 1 |
| `👩‍💻` | 11 | 3 | 5 | 1 |

因此，设计「最多输入 20 个字符」时，需要先决定限制的是字节、码点还是字素簇。按字节截断可能切断 UTF-8 序列；按码点截断也可能拆开组合字符或 Emoji。

## Python 与 JavaScript 为什么会给出不同长度

Python 的 `str` 按 Unicode 码点提供常见的长度与索引操作；JavaScript 字符串的长度与索引则以 UTF-16 码元为单位。

Python 中：

```python
text = "👩‍💻"
print(len(text))                   # 3
print(len(text.encode("utf-8")))   # 11
```

JavaScript 中：

```javascript
const text = "👩‍💻";
console.log(text.length);                         // 5 个 UTF-16 码元
console.log([...text].length);                    // 3 个码点
console.log(new TextEncoder().encode(text).length); // 11 个 UTF-8 字节

const segmenter = new Intl.Segmenter("zh", { granularity: "grapheme" });
console.log([...segmenter.segment(text)].length); // 1 个字素簇
```

这些结果采用了不同的计量单位。对于合法 Unicode 文本，JavaScript 的字符串迭代可以按码点访问，而普通索引仍然按码元访问。语言定义的操作语义，也不能直接当作引擎内部内存布局的说明。

字体则负责另一层工作：同一个码点可以在不同字体中显示为不同形状；多个码点也可能参与一个字形。遇到缺字方框时，需要检查字体支持，不能仅凭显示异常就认定原始字节的编码错了。

## 看起来一样的文字，怎样比较

两种 `é` 可以显示相同，直接进行字符串比较却得到不同结果：

```python
import unicodedata

a = "\u00e9"
b = "e\u0301"

print(a == b)  # False
print(unicodedata.normalize("NFC", a) ==
      unicodedata.normalize("NFC", b))  # True
```

Unicode 规范化为特定等价关系提供一致表示：

| 形式 | 主要过程 |
| --- | --- |
| NFD | 规范分解与重排 |
| NFC | 规范分解、重排，再按规则组合 |
| NFKD | 兼容分解与重排 |
| NFKC | 兼容分解、重排，再按规则组合 |

规范等价用于处理这类组合与分解表示；兼容等价还会合并某些排版或形式区别。例如，NFKC 可以把全角字母 `Ａ` 和带圈数字 `①` 转为 `A` 与 `1`。

选择规范化形式，要看任务希望保留哪些区别。搜索、去重与原始文本存档可能有不同要求。规范化、大小写折叠和排序规则也各自解决不同问题。

规范化还可能改变码点序列和编码后的字节。因此，讨论文本能否原样还原时，需要说明是否做过规范化等预处理。

## 乱码发生在哪一步

处理文件与网络数据时，程序需要在文本和字节之间转换：

```text
文本 → encode → 字节 → 保存或传输 → 字节 → decode → 文本
```

如果编码与解码采用不同规则，就可能产生错误文本：

```python
original = "café"
raw = original.encode("utf-8")
wrong = raw.decode("latin-1")

print(raw.hex(" ")) # 63 61 66 c3 a9
print(wrong)        # cafÃ©
```

最后两个 UTF-8 字节本来共同表示 é，却被另一种规则分别解释成字符。若中间没有发生替换或信息丢失，这个特定过程可以反向恢复：

```python
wrong = "cafÃ©"
restored = wrong.encode("latin-1").decode("utf-8")
print(restored)  # café
```

但已经丢弃的字节或替换掉的字符，通常不能只靠错误显示后的文本完整恢复。因此，排查时应尽量查看原始字节与实际使用的编解码规则。

### 遇到非法字节时

以缺少最后一个字节的「猫」为例：

```python
raw = b"\xe7\x8c"

try:
    raw.decode("utf-8", errors="strict")
except UnicodeDecodeError:
    print("UTF-8 序列不完整")

print(raw.decode("utf-8", errors="replace")) # �
print(repr(raw.decode("utf-8", errors="ignore"))) # ''
```

`strict` 报告错误，`replace` 产生替换字符，`ignore` 丢弃无法解码的部分。它们对应不同的数据处理结果。

### 文件、编码声明与转义

读写文本文件时，可以显式指定编码：

```python
from pathlib import Path

path = Path("unicode-example.txt")
path.write_text("猫😀", encoding="utf-8")

print(path.read_bytes().hex(" ")) # e7 8c ab f0 9f 98 80
print(path.read_text(encoding="utf-8")) # 猫😀
```

HTML 中的 `<meta charset="UTF-8">` 和 HTTP 中与编码相关的声明，帮助接收方选择解释规则；修改声明本身，并不会自动把原有文件转成另一种编码。

源代码里的转义则属于书写规则：

```python
text = "\u732b"
literal = r"\u732b"

print(text, len(text))       # 猫 1
print(literal, len(literal)) # \u732b 6
```

第一个字符串包含「猫」，第二个包含反斜杠、u 和四个十六进制数字字符。看到 `\uXXXX` 时，需要结合所在语言或数据格式，判断它是转义语法还是普通文本。

## 与 Tokenization 衔接

理解这些表示单位后，就可以继续追踪语言模型的输入：

```text
文本 → UTF-8 字节 → tokenizer 的片段 → token ID
```

「猫」的 Unicode 码点是 29483，UTF-8 字节值是 231、140、171；某个 tokenizer 分配的编号，则取决于它的词表。它们分别属于字符标准、字节编码和模型输入表示这几个层次。

在字节级 tokenization 中，一个 token 可能包含多个字符，也可能只覆盖一个字符的一部分字节。解码时通常要先拼接各 token 的字节，再按 UTF-8 还原文本。

这些区别正是 [Tokenization：从文本到 Token 序列](/blog/cs336-tokenization/) 中需要用到的背景。比较字符数、字节数和 token 数时，先说清楚采用的单位，才能解释它们为什么不同。
